# 4.1 Roaming Service — Architecture Overview

The roaming subsystem follows the industry **Roaming Assurance & Steering-of-Roaming (SoR)**
reference architecture: a layered pipeline that acquires signalling from the roaming border,
decodes it, runs it through two processing engines (steering protection + performance assurance),
correlates it against a metadata store, and feeds the NOC and BI consumers.

> Diagram: [`roaming-architecture.puml`](roaming-architecture.puml).

## The five layers

**1 · Roaming Border Network** — the network elements that carry roaming signalling and traffic:
`HLR/HSS/UDM`, `MSC/VLR`, `MME/AMF`, `SGSN`, `SGW/PGW/UPF`, `DRA/DEA`, `STP`, `SMSC`, `IMS`.
Data is acquired **non-intrusively** — passive taps, mirrored ports, Diameter Gx/Rx probes, and
**CDR feeds** (TAP/RAP, NRTRDE).

**2 · Mediation & Collection Layer** — **protocol decoders** that normalise the many roaming
protocols into a common event model: `MAP/CAP`, `Diameter`, `SIP/IMS`, `GTP-C/U`, `SS7-over-IP`,
and `HTTP/2` (5G SBI).

**3 · Processing Engines** (run in parallel, with a feedback loop):
- **Steering Protection Engine** — SoR dispatch orchestration, Ack/timeout detection,
  anti-steering detection, and compliance scoring. It sends **compliance data / risk ratings** to
  the assurance engine.
- **Performance Assurance Engine** — KPI computation, SLA-breach detection, a test-call scheduler,
  and trend/reporting. It sends a **priority signal** back to the steering engine.

**4 · Metadata & Correlation Store** — the shared context both engines read/write: **NE**,
**session**, **user**, **terminal**, and **roaming-agreement** metadata (RAEX/RADB link, IR.21,
SLA). This is what turns raw events into correlated, partner-aware insight.

**5 · Consumers** — **Alarming/Ticketing (NOC)** for operational response and
**Dashboards/Reporting (BI)** for analysis and KPIs.

## Mapping to *our* implementation (`roaming-analysis-service`)

Our Spring Boot service implements a **vertical slice** of this reference architecture — the
**assurance / analytics** path driven from **CDR feeds** — and treats the live-protocol and SoR
layers as the reference frame / roadmap. Honest scope:

| Reference layer | In our service | Status |
|-----------------|----------------|--------|
| Border network — **CDR feeds** | The real `Data/Data` dataset (CDR/TAP-RAP, attach, QoS, handover) is our acquisition point | ✅ Implemented (CDR feed slice) |
| Border network — live **taps/probes** (SS7/Diameter) | Not implemented — we consume *mediated CDRs*, not live signalling | ⛔ Reference only |
| **Mediation / protocol decoders** | `ingest/CsvDataLoader` + `RoamingEventCsvParser` normalise CDR/attach/QoS/handover CSVs into a common event model | ◐ Partial (CDR mediation, not protocol decode) |
| **Performance Assurance Engine** | `RoamingInsightsService` — `/qos`, `/experience` (KPI), `/forecast` (trend), `/live`, `/revenue`, `/optimization`; `/simulate` ≈ test-call scheduler | ✅ Implemented |
| **Steering Protection Engine** (SoR) | Not implemented — no SoR dispatch/anti-steering yet; compliance ≈ our fraud/anomaly scoring | ⛔ Roadmap |
| Compliance / risk scoring | `analysis/RiskAnalyzer` (0–100 heuristic) + `AnomalyDetector` (z-score composite) + dataset `fraud_flag` | ✅ Implemented |
| **Metadata & Correlation Store** | JPA entities `Device` (terminal), `NetworkCell` (NE), `RoamingCdr`/`SessionQos` (session), IMSI (user), in MySQL | ◐ Partial (agreement/IR.21/SLA metadata not modelled) |
| **Alarming / Ticketing (NOC)** | `/anomalies` emits severity-graded alerts (CRITICAL/WARNING/INFO); no ticketing integration | ◐ Partial (alerting, no NOC/ITSM hook) |
| **Dashboards / Reporting (BI)** | Angular Security-Analyst **Roaming** console (Overview/Events/Anomalies/Partners/QoS/Revenue/Tools) + Grafana | ✅ Implemented |

### What this means for the report/defence
- Present 4.1 as the **target reference architecture** (credible, industry-aligned).
- Then state clearly: *"This project realises the **CDR-driven assurance & analytics** vertical —
  mediation of CDR feeds, KPI/QoS/forecast/revenue assurance, and fraud/anomaly compliance scoring,
  surfaced to a BI console — while the live-probe mediation and SoR steering layers are the
  reference frame and roadmap."*
- The honest **Implemented / Partial / Roadmap** split is a strength, not a weakness — it shows you
  understand the full domain and scoped a deliverable within it.

## Roadmap to widen the slice
1. **Roaming-agreement metadata** — model IR.21 / RAEX / SLA per partner operator → real SLA-breach
   detection (not just QoS thresholds).
2. **Steering Protection Engine** — add SoR dispatch + anti-steering detection over `attach_events`
   (welcome-SMS / redirect patterns), with compliance scoring per partner.
3. **NOC hook** — push `/anomalies` alerts to a ticketing webhook (or the platform's
   messaging/notification bus) instead of pull-only.
4. **Live mediation** — beyond CDRs: consume free5GC 5G-SBI (HTTP/2) signalling for the AMF/SMF
   attach/session events (ties into the anomaly-detection-service).
